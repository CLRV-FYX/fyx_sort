# FYX-SORT

这个仓库里有两个排序库，它们**同源但不同路**，代码完全不同，彼此独立。

如果你只是想找一个最快的排序器扔进项目里跑分，往下翻，看 v9.2 那部分。  
如果你想先搞清楚这两个版本到底有什么区别、为什么会有两个，那从开头看起。

---

## 两个版本，两种活法

### v9.1（工程分支）

几个月前上传，是目前仓库里已有的版本。

它的设计目标是**稳妥**。内部实现了工作窃取队列、运行时 CPUID 检测、自适应数据分布学习、显式的 Options 配置、稳定排序接口、内存限额管控。代码分了二十几个模块，可读性相对好一些。

如果你需要：

- 在公司的长期项目里使用
- 支持 `stable_sort`
- 控制内存上限，防止 OOM
- 在不同 CPU 上自适应降级（AVX-512 → AVX2 → SSE4.2）
- 频繁调用，不想每次都新建线程

用 v9.1。它已经在线上跑了一段时间，虽然不能说毫无瑕疵，但至少是朝着工业级方向设计的。

### v9.2（竞赛 / 性能分支）

这个版本今天才放出来，之前一直躺在本地的草稿箱里。

它的设计目标只有一条：**把数字排得尽可能快**。不关心优雅，不关心可配置，不关心异常安全，不关心会不会把内存吃光——只关心吞吐量。

v9.2 基于的代码从未以任何版本号公开过（v9.0 只存在于本地），它和 v9.1 没有任何代码继承关系。如果你看到它内部用了 `std::async`、用了大量宏、没有 Options 结构体，那不是退化，那是故意的。它就是要用最直接的方式把 CPU 跑满。

如果你需要：

- OJ 刷榜
- 离线批处理，跑完就退
- 压测单机极限性能
- 代码量小，拷进去就用的头文件

用 v9.2。它的寿命预期是一次排序调用，不是三年维护周期。

---

## 那 v9.2 到底能跑多快

说几个大概的数字，基于 x86_64，GCC 11，`-O3 -march=native`：

- 100 万个随机 int：约 15~25 ms，比 `std::sort` 快 2~3 倍
- 1000 万个随机 int：约 180~280 ms，比 `std::sort` 快 2.5~4 倍（并行加持）
- 1 亿个随机 int：约 2.5~4 秒，比 `std::sort` 快 2~3.5 倍
- 已排序数据：预扫描直接返回，耗时 0.001 ms 级别
- 小范围整数（0~100）：计数排序 O(n)，不管数据多大都是一两趟扫描的事

这些数字在不同的 CPU、内存频率、编译器版本下会有波动，但整体趋势不会变：**它比标准库快，而且快得不是一星半点**。

---

## v9.2 是怎么做到的

内部混合了以下算法，运行时自动选择：

- 排序网络（n ≤ 12，手工展开，无分支）
- 插入排序（n ≤ 40，带哨兵）
- 内省排序（IntroSort，三路 / 双轴混合分区）
- 基数排序（32 位、64 位、浮点数，LSD 法）
- 计数排序（数值范围 ≤ 400 万时触发）
- 并行快速排序（n ≥ 100 万且核心数 > 1）
- 并行基数排序（n ≥ 500 万且核心数 > 1）

预扫描阶段会检查数据是否已升序、降序或全等，如果是就直接返回或反转，不浪费任何时间。

对于浮点数，它把二进制位映射成无符号整数再排，正负零和 NaN 的处理虽然不算完美，但在绝大多数场景下结果都是对的。

## 怎么用 v9.2

整个库就是一个头文件，没有 `.cpp` 需要编译。

```cpp
#include "fyx_sort.hpp"

std::vector<int> data = {5, 3, 8, 1, 9, 2};
FYX::sort(data);
```

裸数组：

```cpp
int a[100];
FYX::sort(a, a + 100);
```

自定义比较器：

```cpp
FYX::sort(data, std::greater<int>());
```

支持 `vector`、`array`、`deque`、`string`、`list`、`forward_list`、`stack`、`queue`、`priority_queue`、`bitset`、`unordered_set`、`unordered_map` 等常见容器。对于 `set` 和 `map`，排序是空操作——它们本身就有序。

竞赛模式：在文件顶部取消注释 `#define FYX_LG_COMPETITION 1`，编译后会得到一个自带快速 IO 的 `main`，可以直接提交到洛谷之类的 OJ。

## 编译

C++17 是硬性要求。推荐：

```bash
g++ -std=c++17 -O3 -march=native -pthread your_program.cpp
```

MSVC：

```bash
cl /EHsc /std:c++17 /O2 /arch:AVX2 your_program.cpp
```

如果不用并行，可以去掉 `-pthread`，但并行默认是开启的，留着他不会吃亏。

## v9.2 的代价

速度快是有代价的，v9.2 在这些地方做出了明确的取舍：

- **内存占用高**：基数排序和计数排序都需要额外的 O(n) 缓冲区。1 亿个 64 位整数需要 800 MB 的 buffer，加上原数组共 1.6 GB。如果分配失败，它会回退到内省排序，但不保证数据完整性——这个分支没有为“优雅降级”写过任何防御代码。
- **并行实现简陋**：用的是 `std::async`，每次排序调用都会创建一批线程。如果你在一个循环里反复调用，线程创建开销会吃掉所有性能增益。高频场景请用 v9.1 的工作窃取队列。
- **非 x86 平台性能打折**：AVX2、预取指令在 ARM 上不存在，基数排序的 SIMD 优化无法生效。虽然能跑，但不会比 `std::sort` 快多少。
- **不稳定**：所有快排和基数排序实现都是不稳定的。相同元素的相对顺序会被打乱。如果你依赖稳定性，要么用 `std::stable_sort`，要么切到 v9.1。
- **异常安全约等于零**：如果排序过程中内存分配失败，它不会抛异常然后优雅退出，而是尽量往下走，但结果可能是一堆乱序数据。v9.2 的哲学是“默认内存足够，默认不会失败”，如果你觉得这个假设不成立，v9.1 更合适。

## 测试

定义 `FYX_RUN_TESTS` 且不定义 `FYX_LG_COMPETITION` 时，会编译出独立测试程序：

```bash
g++ -std=c++17 -O3 -DFYX_RUN_TESTS -pthread fyx_sort.hpp -o fyx_test
./fyx_test
```

测试覆盖排序网络（n=2~12 重复 2000 次）、整数 / 浮点 / 长整型、已排序 / 逆序 / 全等 / 小范围 / 模 3 杀手数据 / 管风琴分布、链表 / deque / string / bitset / 自定义结构体、并行排序正确性。

性能测试会同时跑 `std::sort` 做对照，输出加速比和内存增量。

## 那到底该用哪个

如果你还在犹豫，这里有一个简单粗暴的判断标准：

- 你的代码要在生产环境里跑一年以上 → 用 v9.1
- 你的代码跑完一次就退出，或者跑完输出结果就结束 → 用 v9.2
- 你需要稳定排序 → 用 v9.1（或者 `std::stable_sort`）
- 你需要在 OJ 上刷榜 → 用 v9.2
- 你需要在 ARM 服务器上跑 → v9.1 适配性更好，v9.2 不确定
- 你想把代码拷进一个已有项目里，不想改任何构建脚本 → v9.2 更合适（单头文件，拷进去就能用）
- 你愿意花几分钟配置 Options 和内存限额 → v9.1 可控性更强

两个版本我都不会说“另一个是垃圾”，它们只是面对不同场景的不同答案。如果你的场景两边都沾一点，那就两个都留着，按需切换。
